01 · Overview

  
The problem

  
Every payroll deposit and auto-pay bill in the US moves over ACH as fixed-width text files. A receiving bank gets those files from the ACH operator, and for every entry it must decide: can this be posted to one of our accounts, or does it go back with a return code? The files are large, they arrive on a schedule, and the same account can be hit by many entries at once. Correctness under concurrency is the whole job.


  

    
GOAL
Never process a file twice
Files are claimed with an atomic filesystem rename, and the file's SHA-256 is unique in the database as a second line of defence.

    
GOAL
Never count a debit twice
Entry evaluation is idempotent: only PENDING entries are touched, and status plus daily usage commit in a single transaction.

    
GOAL
Scale out per file
Entries are split into chunks and checked in parallel by a Celery chord; one callback reconciles the file once every chunk is done.

  

  

    
IN SCOPE
  • Inbound NACHA files (PPD / CCD), record types 1 5 6 7 8 9
  • Structural validation: record lengths, control totals, entry hash
  • Per-entry checks: routing check digit, account status, daily debit limit
  • Test-data generator and account seeding for repeatable demos

    
OUT OF SCOPE (FOR NOW)
  • Real money movement and Fed connectivity (mocked in v0.4)
  • Originating outbound files
  • OFAC screening beyond a mock sanctions check
  • Multi-tenant banks

  







  

    
02 · Architecture

    
A chain that fans out into a chord

    
Beat wakes the scanner every minute. Each claimed file gets its own Celery chain: ingest, then build a chord of parallel entry checks whose results are reconciled by one callback. Only IDs and paths ever cross Redis; PostgreSQL holds the truth.

  


  

    
    

      Celery task · tasks.py
      Plain function · services.py / checks.py
      Scheduler
    

  


  

    
1 · CLAIM
Atomic rename
Senders write .tmp, then rename to .ach. The scanner claims a file by renaming it into processing/. Only one process can win.

    
2 · INGEST
Parse + reconcile
Fixed-width parse, control totals and entry hash verified, then file, batches and entries saved in one transaction.

    
3 · FAN OUT
Chunk + chord
PENDING entry IDs are split into chunks of ACH_CHUNK_SIZE, and each chunk becomes a parallel check_entries task.

    
4 · RECONCILE
One callback
The chord's result backend counts completions; finalize_file receives every summary and marks the file CHECKED.

  



# tasks.py: thin tasks, fat services
chain(process_file.s(path), check_file.s()).delay()          # one chain per claimed file

@shared_task(bind=True)
def check_file(self, file_id):
    ids = pending_entry_ids(file_id)
    if not ids:
        return finalize_file([], file_id)
    header = group(check_entries.s(c) for c in chunked(ids, settings.ACH_CHUNK_SIZE))
    chord(header, finalize_file.s(file_id)).delay()      # body receives [summary, …]







  

    
03 · The format

    
NACHA, 94 characters at a time

    
A NACHA file is a strict hierarchy of fixed-width records. Every line is exactly 94 characters, the file is padded to a multiple of 10 lines with filler records of nines, and every level carries control totals that must reconcile with the level below.

  


  

    
1
File Header · immediate destination / origin, creation date

    
5
Batch Header · company, SEC code (PPD/CCD), effective date

    
6
Entry Detail · transaction code, RDFI routing, account, amount, trace

    
6
Entry Detail · …

    
7
Addenda (optional)

    
8
Batch Control · entry count, entry hash, debit / credit totals

    
9
File Control · batch count, block count, file totals

    
9…
9999999999…  filler to a multiple of 10 lines (blocking factor)

  


  

    
Entry Detail (record 6), hover a field. Positions are 1-based, inclusive.

    

  


  

    

      INTERACTIVE
      
ABA routing check digit

      
The 9th digit of a routing number is a checksum over the first eight, using weights 3-7-1. Type any 8 digits.

      

      

      

      

    

    

      RECONCILIATION
      
Totals that must agree

      
    
        
  • Entry hash: sum of the 8-digit RDFI routing numbers, keeping the rightmost 10 digits
    • 
        
  • Debit / credit totals: per batch, from transaction codes (2nd digit 2/3 = credit, 7/8 = debit)
    • 
        
  • Counts: entries per batch, batches per file, 10-line blocks per file
    • 
        
  • Trace numbers: ODFI routing (8) + 7-digit sequence, unique per file
    • 
      

      
Any mismatch raises AchFormatError and the whole file is rejected before a single row is written, because ingest runs in one transaction.


def check_digit(routing8):
    w = (3,7,1,3,7,1,3,7)
    total = sum(int(d)*k for d, k in zip(routing8, w, strict=True))
    return str((10 - total % 10) % 10)

05 · Entry validation

    
Pure checks, first failure wins

    
Each check is a pure function: plain values in, an R-code or None out. No database access, so every branch is unit-tested in milliseconds. The service layer loads data in bulk and runs the checks in order; Python's or short-circuits on the first failure.

  

  

    
1
R28
Routing check digit error
check_routing()

    
2
R03
No account / unable to locate
check_account(None)

    
2
R02
Account closed
check_account()

    
2
R16
Account frozen
check_account()

    
3
R01
Over daily debit limit*
check_limit()

  

  
* NACHA has no limit-specific return code; using R01 for a velocity breach is a documented bank-policy choice. Credits are never limit-checked.

06 · Concurrency & correctness

    
Why the row locks exist

    
Two chunks can hold debits for the same account. Each one reads today's usage, adds its debit, and writes it back. Without a lock, one write silently erases the other, and an account sails past its limit. Run it both ways:

  


  

    

      
      
    

    
    

      
chunk A · worker 3

      

        
DailyUsage.used_cents · limit 50,000

        
40,000

        

        

      

      
chunk B · worker 7

    

  


  

    
LOCKING
Lock rows, in order
Usage rows are created if missing (ignore_conflicts on the unique key), then locked with select_for_update().order_by("id"). A consistent lock order means no deadlocks.

    
IDEMPOTENCY
Retries are harmless
Only PENDING entries are evaluated, and status changes and usage increments commit together. A retried or duplicated task finds nothing left to do.

    
MESSAGES
IDs, never payloads
Redis carries paths, file IDs and lists of entry IDs. Every task re-reads fresh rows inside its own transaction, so nothing goes stale in a queue.

  







  

    
07 · Design decisions

    
Trade-offs, written down

  

  

    
Separate ingest from evaluation
Checking inside the parser would save one UPDATE, but it would couple file-format validation to bank data, hold usage locks for the whole ingest, and leave nothing to fan out. Keeping them apart makes ingest pure, checks parallel, and either step re-runnable.
rejected: single-pass parse-and-check

    
A DailyUsage table, not a column on Account
A used_today column needs a midnight reset job, can't represent late or future-dated files, and keeps no history. One row per (account, date) needs no reset and gives a natural row to lock.
rejected: Account.used_today_cents + nightly reset

    
Thin tasks, fat services
Tasks only move IDs and call services. Business logic stays plain Python, testable without a worker, callable from a view, the shell or a task, and unchanged when orchestration moves from a loop to a chord.
rejected: logic inside @shared_task bodies

    
The filesystem rename is the lock
A rename within one filesystem is atomic, so concurrent scanners can't both claim a file and no Redis lock is needed. SHA-256 uniqueness backs it up against the same content under a new name.
rejected: Redis lock around scan_incoming (for now)

    
Return codes, not booleans
A check that says only "no" loses the reason the bank must report. Returning None or an R-code keeps the verdict and the reason together, and still composes with or.
rejected: bool + re-inspection by caller

    
Trace numbers unique per file
Trace sequences restart in every file, so a global unique index rejected valid files. The constraint is scoped to (file, trace_number), matching how the network actually behaves.
rejected: globally unique trace_number

09 · Testing

      
Fast where it can be

      
Pure unit tests
Parametrized tables for every check branch and the check digit, including boundaries like a debit landing exactly on the limit. No database, no worker.

      
Database tests
pytest-django builds a throwaway test database; each test creates the accounts it needs and rolls back. Golden fixtures cover a good file and a file with bad totals.

      
Layout tests
Record layouts are asserted to cover all 94 characters with no gaps or overlaps, so a typo in a field position fails CI, not production.
