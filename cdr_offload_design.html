CDR Offload
Service

An async pipeline that watches a directory for telecom call‑detail records, validates and idempotently loads them into MongoDB, and exposes the result through a metrics‑instrumented REST API.

Python 3.11 asyncio Pydantic v2 PyMongo Async FastAPI Prometheus / Grafana Docker Compose
Overview

What this is

A Call Detail Record (CDR) is written by a phone system every time a call completes — who called whom, when, for how long, and how the call was routed. In a real deployment these arrive as flat CSV files that need to be picked up, validated, and moved into a queryable store without dropping a row or double‑counting one, even when the same file gets reprocessed after a crash.

This service does exactly that. It watches an incoming directory, waits for each file to finish being written, parses and validates every row, and upserts the result into MongoDB using the record's own unique call ID as the primary key — so replaying the same file twice overwrites, it never duplicates. Rows that fail validation are quarantined instead of dropped. The pipeline reports its own health through Prometheus, and a separate FastAPI service exposes the stored records for search, update, and deletion over REST.

Data Flow

One record's journey

  1. A CSV file — from gen_cdrs.py, or a real PBX — lands in the bind‑mounted incoming/ directory.
  2. The producer polls the directory every 100–500ms and tracks each new file's size; once the size hasn't changed for 2 seconds, the file is considered fully written and gets queued.
  3. One of three consumer workers pulls the filename off the asyncio.Queue and opens it for reading.
  4. Each row is parsed with csv.DictReader and validated against CdrRecord — type coercion, required fields, and a blank‑to‑None rule for the optional answer timestamp.
  5. A row that fails validation is appended to dead_letter/failed_<filename>.csv; a row that passes is upserted into MongoDB with $set, using its uniqueid as _id.
  6. Every file processed, row processed, row failed, and upsert duration increments a Prometheus counter or histogram exposed on the consumer process's own :8000/metrics.
  7. Prometheus scrapes that endpoint every 5 seconds; Grafana queries Prometheus to render throughput and p50/p95 upsert latency.
  8. A separate FastAPI process — its own MongoDB connection, its own container — serves POST, GET, PATCH, and DELETE against the same cdrs collection, for anything that needs to search, correct, or remove a record after the fact.
Design Decisions

Why it's built this way

IDEMPOTENCY

Using uniqueid as Mongo's _id turns every write into update_one(…, upsert=True) instead of insert_one — reprocessing a file after a crash overwrites the same documents instead of duplicating them. Tradeoff: uniqueness is only as good as the source system's ID scheme, since there's no server‑generated ObjectId to fall back on.

FILE‑STABILITY DETECTION

A CSV mid‑write looks, for a moment, like a file that's safe to read. The producer tracks each file's size across polls and only enqueues it once the size holds steady for 2 seconds — a cheap debounce that avoids reading a half‑written row.

FAIL‑OPEN VALIDATION

One malformed row doesn't abort the file. CdrRecord validation failures are caught per‑row, written to a dead‑letter CSV alongside the original header, and the loop continues — every file is fully drained, either into Mongo or into the dead letter, never left half‑processed.

OBSERVABILITY IS PER‑PROCESS

prometheus_client's registry lives in memory, scoped to one Python process. The watcher and the API run as separate containers, so each exposes its own /metrics rather than assuming a shared registry — the same reason each service configures its own logging.basicConfig() instead of inheriting one.

SEPARATE QUERY SERVICE

The watcher's job is throughput: drain files, never stop. The API's job is availability: answer a request now. Splitting them into two containers means a slow query from a client can't back up file processing, and a burst of incoming files can't make the API time out.

HEALTHCHECK‑GATED STARTUP

Both cdr and api wait on Mongo's healthcheck (mongosh ping) rather than just its container start — Mongo's process can be "up" seconds before it's actually ready to accept connections.

Local Setup

Running a script outside Docker

docker compose up --build handles dependency installation inside the container automatically. Running a file directly on the host — for quick iteration or debugging — requires a virtual environment set up first, on a fresh checkout:

  1. python3 -m venv venv — create an isolated environment in venv/.
  2. source venv/bin/activate (venv\Scripts\activate on Windows) — point python and pip at it.
  3. pip install -r requirements.txt — install the pinned dependencies into it.

gen_cdrs.py is the only script with no external dependency — it just writes CSVs — so it's the fastest way to sanity‑check a fresh venv. cdr_processor.py, mongo_processor.py, and api_data.py all expect a reachable MongoDB, so running them standalone also means a local Mongo instance — via Docker or otherwise — needs to already be up.
