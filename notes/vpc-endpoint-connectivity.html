Operational Note: Troubleshooting AWS VPC Endpoint Connection Timeouts

Tags: AWS, Networking, PrivateLink, Security Groups, DNS Triaging

The Situation

To comply with strict air-gapped security frameworks for our high-concurrency architecture, all traffic between localized application workers running in private subnets and upstream AWS services (or isolated backend services) must remain entirely within the AWS internal network backbone. Public Internet Gateways (IGW) or NAT Gateways were intentionally bypassed by provisioning an AWS Interface VPC Endpoint (PrivateLink) to route traffic natively via Elastic Network Interfaces (ENIs) mapped into our subnets.

The Hurdle: Silent Connection Timeouts

Upon deploying a secondary microservice service instance, client container threads attempting to query the endpoint dropped into a hanging state, ultimately crashing with unhelpful connection gateway timeouts:

HTTP/1.1 504 Gateway Timeout
Dial tcp 10.0.4.12:443: i/o timeout

Because the request did not immediately return a Connection Refused flag, it indicated that routing primitives were sending traffic to the right place, but packets were being silently dropped on the floor without a response handshake.

Diagnostic Steps & Root Cause Triaging

Isolating the breakdown required stripping out application layer noise and systematically validating the low-level infrastructure dependencies:

1. Transport Layer Isolation

Executing an interactive network scan from within the client container verified that the connection was fundamentally blocked at the socket layer:

# Testing raw TCP connection to the VPC Endpoint private IP
$ nc -zv 10.0.4.12 443
Connection to 10.0.4.12 443 port [tcp/https] timed out

2. DNS Split-Horizon Verification

We verified that the container was correctly attempting to resolve the private IP address of the endpoint rather than leaking out to public internet addresses:

$ dig s3.us-east-1.amazonaws.com
;; ANSWER SECTION:
s3.us-east-1.amazonaws.com. 60 IN A 10.0.4.12
s3.us-east-1.amazonaws.com. 60 IN A 10.0.12.34

DNS resolution was functioning exactly as expected because Enable Private DNS Name was flagged on the VPC Endpoint setup, proving the local Route 53 resolver was properly catching the queries.

3. Discovering the Security Group Mismatch

The root bottleneck traced directly to an asymmetric AWS Security Group configuration rule block. Interface VPC Endpoints provision managed ENIs directly inside your subnets, and those ENIs are governed by their own specific security group. While the client microservice possessed correct outbound egress rules, the *Endpoint's security group* lacked an inbound rule explicitly authorizing ingress traffic on port 443 from the client's Security Group ID or subnet CIDR range.

The Fix & Operational Verification

To remediate the silent timeout failure and restore non-blocking connectivity, we executed the following infrastructure adjustments:

  1. Applied Inbound Security Group Hooks: Modified the Terraform configurations mapping the VPC Interface Endpoint to append a definitive ingress allowance: 
    # Target Security Group: sg-endpoint-rules
Type: Inbound | Protocol: TCP | Port Range: 443 | Source: sg-client-service-id
  2. Availability Zone (AZ) Realignment: Verified that the subnets selected for the endpoint matched the exact availability zones where our processing nodes were actively running, preventing cross-AZ latency overhead.

Immediately upon committing the security group modifications, we verified the resolution from the application container environment:

$ nc -zv 10.0.4.12 443
Connection to 10.0.4.12 443 port [tcp/https] succeeded!

$ curl -I https://s3.us-east-1.amazonaws.com
HTTP/1.1 200 OK
Key Operational Lesson: Whenever a service connection hangs silently in AWS without returning an immediate RST (reset) packet, prioritize validating the inbound rules of the *receiving* target infrastructure's security group. If a security group denies inbound traffic, it silently drops the packets instead of explicitly rejecting them.
