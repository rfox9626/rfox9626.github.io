High-Concurrency E-Commerce Engine & Fulfillment Pipeline

System Architecture & Technical Design Specifications

Core Stack: Golang, PostgreSQL, Redis, Kafka
Architecture Pattern: Event-Driven, CQRS, Outbox Pattern
Concurrency Strategy: Optimistic Locking & Distributed Leases
Target SLA: p99 Latency less than 50ms under peak load

1. Executive Summary & Core Challenges

This document details the architectural specifications for a distributed, high-throughput e-commerce core designed to eliminate common runtime hazards under heavy seasonal traffic surges. The system isolates and resolves three classic transactional bottlenecks:

  • Inventory Race Conditions: Preventing overselling during flash-sale concurrency spikes without relying on heavy, database-level blocking table locks.
  • Decoupled Payment Processing: Ensuring third-party API latencies (e.g., payment gateways) never degrade the throughput of the primary customer checkout experience.
  • Atomic Ledger Reliability: Guaranteeing absolute consistency between order placements, financial tracking data, and downstream fulfillment logs.

2. Distributed Event-Driven Flow

The system decouples the highly critical user-facing checkout process from slow, external third-party services by converting synchronous API operations into an asynchronous event stream driven by a resilient messaging ring.

[Client Request] 
       │ (REST / Go Gin API)
       ▼
[Order Service] ──(Atomic Local Write)──> [PostgreSQL DB (Order + Outbox Table)]
       │
       ▼ (Transactional Outbox Poller / Debezium CDC)
  [Kafka Topic: order.events.validated]
       │
       ├──> [Payment Worker] ──> External Gateway (Stripe/PayPal API)
       │
       └──> [Inventory Worker] ──> Local State Deduplicator & Allocator
       │
       └──> [Fulfillment Microservice] ──> Packing / Shipping Pipeline Warehouse Dispatch

3. Concurrency Strategy & Race Condition Prevention

To scale past traditional database write-blocks, the core inventory system drops raw SELECT FOR UPDATE paradigms. Instead, it utilizes a dual-layer concurrency mechanism:

Layer 1: In-Memory Pre-Allocation (Redis)

Stock quantities are mirrored inside Redis hashes. Immediate inventory checks and reservation subtractions are validated atomically via Lua scripts running single-threaded execution passes directly inside the memory layer. This weeds out 99% of invalid requests instantly before they can impact relational disk storage assets.

Layer 2: Optimistic Database Concurrency Control (OCC)

When write-back routines persist adjustments down into the relational PostgreSQL core, the transactions utilize a strict operational versioning check:

UPDATE inventory_sku 
SET stock_quantity = stock_quantity - :quantity, version = version + 1
WHERE sku_id = :sku_id AND version = :current_version;

If another database worker commits an update first, the version mismatch is flagged immediately, triggering an asynchronous worker back-off and retry loop sequence.

4. Transactional Integrity (The Outbox Pattern)

Design Rule: A microservice must never execute a local database write and concurrently publish a message to a distributed broker within a raw code block, as network splits risk leaving the systems in mismatched states.

To preserve absolute transactional execution records, the pipeline implements the Transactional Outbox Pattern. Order creations and corresponding system events are written into the same local PostgreSQL transactional boundary using standard ACID properties:

idaggregate_typepayloadstatus
Table: order_outbox Type Purpose
UUID (PK) Unique tracking token for system events.
VARCHAR Defines target domains (e.g., OrderService).
JSONB Complete metadata, schema variants, and payload context.
VARCHAR Lifecycle flag: PENDING, PROCESSED, FAILED.

A highly optimized transaction parser reads this table continuously, streaming messages to Kafka safely before updating the row status to completed.
