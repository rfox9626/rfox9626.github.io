Technical Design: High-Concurrency Order Engine

Author: Richard Fox | Status: Production Design & Implementation

1. Architectural Overview

This system utilizes a decoupled, event-driven architecture to mitigate database contention and handle traffic spikes. By separating the entry point (API Gateway) from processing (Workers), we ensure system availability even when backend services are under load.

Figure 1: Event-Driven Order Processing Pipeline

2. Data Flow & Logic

2.1 The "Happy Path" (Success)

  1. Ingestion: API Gateway receives a POST /order request.
  2. Validation: Go Lambda queries Redis for user restriction status.
  3. Handoff: Validated requests initiate an sqs:SendMessage action.
  4. Buffering: SQS accepts the payload, acting as a pressure valve during bursts.
  5. Processing: Python Lambda triggers, performs rate-limiting/logic, and writes to DynamoDB.
  6. Confirmation: HTTP 202 Accepted returned to client.

3. Error Handling & Failure Modes ("The Sad Path")

Failure Point Symptom Mitigation Strategy
Redis Down Validation failure Fail-Safe: Reject requests if cache is unreachable.
SQS Saturation Queue depth limit Backpressure: API Gateway returns HTTP 429 (Throttling).
Python Lambda Error Execution crash Retry Mechanism: Retries with exponential backoff; moves to DLQ after 3 failures.
DynamoDB Throttle Write capacity limit Jitter/Retry: Automatic AWS SDK retry logic.

4. Security & Access Control (IAM)

4.1 Validator Role (Go Lambda)

Purpose: Read-only access to Redis (VPC) and write access to SQS.

{
  "Effect": "Allow",
  "Action": ["sqs:SendMessage"],
  "Resource": "arn:aws:sqs:region:account-id:OrderQueue"
}

4.2 Processor Role (Python Lambda)

Purpose: Consume queue messages and persist order data.

{
  "Effect": "Allow",
  "Action": ["sqs:ReceiveMessage", "sqs:DeleteMessage"],
  "Resource": "arn:aws:sqs:region:account-id:OrderQueue"
},
{
  "Effect": "Allow",
  "Action": ["dynamodb:PutItem"],
  "Resource": "arn:aws:dynamodb:table/Orders"
}

5. Implementation Examples

Success Scenario

Input: {"user_id": "123", "item_id": "456"}

Result: Order persisted in DynamoDB (Status: PENDING).

Restricted User (Early Termination)

Input: {"user_id": "BANNED_USER", "item_id": "456"}

Result: HTTP 403 Forbidden. The system never touches SQS/DynamoDB, protecting system throughput.

6.2 Architectural Design Decisions

  • Dual ECR Repositories: We decoupled the container registries into two distinct repositories (ecommerce-lambda-v2 and sqs-redis-handler-v2). This isolates deployment lifecycles between the Go API gateway and the Python backend processor, preventing version collisions.
  • Multi-AZ Subnet Allocation: Ensured private subnets are strictly mapped to distinct Availability Zones (e.g., us-east-1a and us-east-1b) to satisfy AWS compliance constraints for ElastiCache Serverless and multi-AZ VPC interface endpoints.
  • CI/CD Pipeline Phasing: Resolved the container-lambda chicken-and-egg deployment puzzle by structuring GitHub Actions into a multi-pass apply strategy: provisioning core infrastructure and ECR skeletons first, pushing compiled Docker images, and finalizing the Lambda deployments.
